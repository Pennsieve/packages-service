# Pennsieve metadata records, version 1.0

Identifier: `https://schemas.pennsieve.io/structures/pennsieve-records`
This version: `https://schemas.pennsieve.io/structures/pennsieve-records/v1.0`
Registry id (app.yml `conformsTo`): `pennsieve-records`, or
`pennsieve-records@1.0` for this version

A dataset's metadata records, as an app reads them. An app asks for them
with an input of this structure; a run fills it from a dataset view, with the
records the view pins. It is the layout of Pennsieve's metadata export
without the `metadata/` prefix. A view can hold one model's records under
several schema versions, so each model has a folder per version.

## Layout

```
models/
  <model>/
    versions/
      <n>/
        schema.json     the model version's JSON Schema (required)
        records.jsonl   its records, one per line (required; may be empty)
relationships.csv       links between records (required; may be only the header)
files.csv               which files records are linked to (records of a published dataset only)
.pennsieve/view.json    the dataset view the records came from, when they came from one
```

- `<model>` is the model's name in its dataset (e.g. `subject`, `sample`):
  lower-case letters, digits and `_`. Models are dataset-specific: an app
  shouldn't assume which ones there are, or should say in its description
  which it expects.
- `<n>` is the schema version, a positive integer. A model has at least one
  version folder, and may have several: each record is in the folder of the
  schema version it was written under. A reader takes every version of a
  model (or says which it expects); fields can be added or removed between
  versions.
- Paths are case-sensitive.
- A run brings exactly these files. Pennsieve's metadata export has others
  (a published dataset's `codebook.json`, for example); a run leaves them
  out, and a reader of a Discover download's `metadata/` folder ignores
  them.

## `models/<model>/versions/<n>/schema.json`

The model version's JSON Schema: an `object` whose
`properties` are the record's fields, with their types and `required`. Pennsieve
annotations on a property include:

| Annotation | Meaning |
|---|---|
| `x-pennsieve-key` | the field is (part of) the record's key |
| `x-pennsieve-unit` | the field's unit, e.g. `"mg"` |
| `x-pennsieve-sensitive` | the field holds sensitive data |

Other `x-pennsieve-*` annotations (common data elements, value sets) may
appear; readers ignore what they don't know.

## `models/<model>/versions/<n>/records.jsonl`

[JSON Lines](https://jsonlines.org/): one record per line, each an object

```json
{"id": "6c1e…", "data": {"subject_id": "sub-01", "age": 34, "sex": "F"}}
```

- `id`: the record's id, unique across the dataset; relationships use it.
- `data`: the record's fields, as the schema describes them. A field without
  a value may be missing.

## `relationships.csv`

CSV with a header row:

```
source_record_id,target_record_id,relationship_type
6c1e…,a92f…,has_sample
```

It may name records that aren't in the folder: a published dataset's table
covers the whole dataset, whichever models were picked. Join on the ids, and
don't assume both ends of a link are present.

## `files.csv`

Only for records from a published dataset. CSV with a header row,
`record_id,package_id,path`: a record's link to a file, where `path` is the
file's path in the published dataset (it starts with `files/`), or empty when
the file isn't in the publication. An app that also takes the dataset's files
gets them without the `files/` prefix: match on `package_id`.

## Reading it

With [DuckDB](https://duckdb.org/), one view per model over all its
versions, its fields as columns and the version as `schema_version`:

```python
import os
from pathlib import Path

import duckdb

root = Path(os.environ["INPUT_DIR"]) / "records"   # the input's folder
con = duckdb.connect()

def lit(s):    # an SQL string literal
    return "'" + str(s).replace("'", "''") + "'"

def ident(s):  # an SQL identifier
    return '"' + str(s).replace('"', '""') + '"'

def read(path):  # a records.jsonl file
    return f"""read_json({lit(path)}, format='newline_delimited',
        sample_size=-1, columns={{'id': 'VARCHAR', 'data': 'JSON'}})"""

for model in sorted((root / "models").iterdir()):
    versions = sorted((model / "versions").iterdir(), key=lambda v: int(v.name))
    # The fields' types, from all records of all versions; none for empty
    # files or records without fields.
    every = " UNION ALL ".join(f"SELECT data FROM {read(v / 'records.jsonl')}" for v in versions)
    fields = con.sql(f"SELECT json_group_structure(data) FROM ({every})").fetchone()[0]
    cols = "id AS record_id"
    if fields and fields.startswith("{") and fields != "{}":
        cols += f", unnest(from_json(data, {lit(fields)}))"
    union = " UNION ALL ".join(
        f"SELECT {int(v.name)} AS schema_version, {cols} FROM {read(v / 'records.jsonl')}"
        for v in versions)
    con.sql(f"CREATE VIEW {ident(model.name)} AS {union}")
# In its own schema, so a model named relationships keeps its name.
con.sql("CREATE SCHEMA links")
con.sql(f"""CREATE VIEW links.relationships AS
    SELECT * FROM read_csv({lit(root / "relationships.csv")}, all_varchar=true)""")
print(con.sql('SELECT * FROM "subject"'))
```

- It reads every version of every model, including an empty `records.jsonl`
  or records without fields: such a model has only `schema_version` and
  `record_id`. A field a version doesn't have is `NULL` in its records; to
  read one version only, filter on `schema_version`.
- Paths and names are quoted as SQL literals and identifiers, so any folder
  or model name works. The relationships are `links.relationships`, apart
  from the models, so a model named `relationships` keeps its name.
- A field named `record_id` or `schema_version` comes out with a suffix (`record_id_1`).
- A field whose values have different types across records, of one version
  or several (a number in one, text in another), comes out as JSON.
