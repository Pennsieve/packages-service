# Plan: Viewer-Asset Tags & Dataset Highlights

Status: **Proposed** — implementation plan, no code changes yet.

## Goal

From the product perspective, two capabilities:

1. **Thumbnail gallery** on the dataset overview page in the Pennsieve App, and on the
   Discover App, SPARC.science, and Epilepsy.science apps (the latter three via the
   public `/discover` API routes).
2. **Dataset highlights** — viewer assets a user has tagged as highlights, retrievable
   as a dataset-level list, with an optional user-defined ordering.

Decomposed into three pieces of functionality:

1. Manage tags on viewer assets (add tag, remove tag).
2. Retrieve dataset highlights — assets tagged with a specific tag (the app will use
   `highlight`), and more generally filter the asset lists by tag and/or `asset_type`
   (e.g. `asset_type = 'thumb'` for the gallery).
3. Manage the order of highlights.

## Current state (what exists today)

- **Viewer assets already exist** and live entirely in **packages-service**
  (`lambda/service/handler/assets.go`, `discover_cloudfront.go`). `datasets-service` has
  **no** asset or CloudFront code and is not involved.
- The `/assets` list endpoint and the public `/discover/assets` endpoint each support
  exactly two modes — package-scoped (`?package_id=`) vs dataset-scoped (no `package_id`).
  **There is no `asset_type` or `tag` filtering today**; `asset_type` is stored and
  returned but never used in a `WHERE` clause.
- **There is no tag concept yet** — no column, no table, no `properties.tags`. Highlights
  are greenfield.
- Reads of asset bytes go through **CloudFront signed policies + cookies**, generated by
  `signDatasetCloudFront()` (auth) and the discover equivalent. Any new read endpoint that
  returns assets reuses this machinery unchanged.
- Schema for `viewer_assets` / `viewer_asset_packages` lives in the
  **pennsieve-db-migrations** repo under `migrations/organization/` (Flyway 4.2.0).

## Decisions

| Decision | Choice |
|---|---|
| Tag storage | New generic `viewer_asset_tags` table. `highlight` is one tag value among many. |
| Ordering | `position INTEGER` column on `viewer_asset_tags`. |
| Owning service | **packages-service** (reuses CloudFront signing; `datasets-service` has none). |
| API shape | Filters on existing routes + a `tags` sub-resource + a highlights-order endpoint. |
| Tag values | Free-form strings — no server-side allowlist. `highlight` is a convention. |
| Default ordering | `ORDER BY position NULLS LAST, created_at DESC` — tagging alone yields a sensible list; explicit reordering is optional. |
| Filter composition | `tag` and `asset_type` filters are orthogonal and combinable. |

## Schema change (pennsieve-db-migrations)

One new **organization-scoped** migration (immutable; created via
`./scripts/generate-migration-file.sh organization create_viewer_asset_tags`):

```sql
-- migrations/organization/V<timestamp>__create_viewer_asset_tags.sql
CREATE TABLE viewer_asset_tags (
  viewer_asset_id UUID NOT NULL REFERENCES viewer_assets(id) ON DELETE CASCADE,
  tag        VARCHAR(255) NOT NULL,
  position   INTEGER,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (viewer_asset_id, tag)
);

CREATE INDEX viewer_asset_tags_tag_idx ON viewer_asset_tags(tag);
```

Notes:

- Matches the existing `viewer_asset_packages` conventions: composite PK, cascade delete,
  plain `created_at` default.
- No `updated_at` trigger — tags are add/remove, not mutate.
- `position` is nullable (NULL = unordered; ordering optional per the decision above).
- **Must be applied on Dev before the packages-service code is deployed there.** The
  migration ships independently of the service.

Ordered-highlights query shape:

```sql
SELECT va.*
FROM viewer_assets va
JOIN viewer_asset_tags t ON t.viewer_asset_id = va.id
WHERE va.dataset_id = $1 AND t.tag = 'highlight'
ORDER BY t.position NULLS LAST, va.created_at DESC;
```

## API changes (packages-service)

All changes in `lambda/service/handler/`.

### 1. List filters — `assets.go` `handleList` (authenticated)

Read `h.queryParams["tag"]` and `h.queryParams["asset_type"]`. Append, to both the
package-scoped and dataset-scoped queries:

- `AND va.asset_type = $N` when `asset_type` is present.
- `AND EXISTS (SELECT 1 FROM "{org}".viewer_asset_tags vat WHERE vat.viewer_asset_id = va.id AND vat.tag = $N)`
  when `tag` is present.
- When `tag=highlight`, order by `vat.position NULLS LAST, va.created_at DESC` (join
  instead of EXISTS so `position` is available for the sort).

Filters are independent and combinable (e.g. `?asset_type=thumb&tag=highlight`).

### 2. Public list filters — `discover_cloudfront.go` `handleListAssets`

Identical filter clauses added to both discover queries. **No auth change** — still
publication-gated via the Discover DB. This is what serves the gallery/highlights to the
Discover, SPARC.science, and Epilepsy.science apps.

### 3. Tag management — new handlers in `assets.go`

- `POST /assets/{id}/tags` — body `{"tag":"highlight"}`. Permission `EditFiles`.
  Verifies the asset belongs to the request's `dataset_id` (same authorization boundary as
  `handleGet`/`handleUpdate`), then `INSERT ... ON CONFLICT DO NOTHING`.
- `DELETE /assets/{id}/tags/{tag}` — Permission `EditFiles`. Dataset-scoped delete.

### 4. Highlight ordering — new handler in `assets.go`

- `PUT /assets/highlights/order?dataset_id=..` — body `{"ordered_ids":["id1","id2",...]}`.
  Permission `EditFiles`. Sets `position` for the listed assets in a single statement:

  ```sql
  UPDATE "{org}".viewer_asset_tags vat
  SET position = o.pos
  FROM (VALUES ($1::uuid, 1), ($2::uuid, 2), ...) AS o(id, pos)
  WHERE vat.viewer_asset_id = o.id AND vat.tag = 'highlight';
  ```

### 5. Routing — `root.go`

Extend the existing `/assets/` prefix branch to sub-parse:

- `/assets/{id}/tags` → `POST` (add), and `/assets/{id}/tags/{tag}` → `DELETE` (remove).
- `/assets/highlights/order` → `PUT`.

The current router already splits `/assets` (exact) vs `strings.HasPrefix(h.path, "/assets/")`.

### 6. Docs — `doc/viewer-assets.md`

Document the new table, the `tag`/`asset_type` filters, and the new endpoints. While there,
fix the pre-existing drift where the doc omits `chat_session_id` / `clear_chat_session`.

### 7. Tests

Follow the existing `assets_test.go` + `testdata/*.sql` pattern for the new filters and
endpoints.

## API summary

```
# reads — auth (Pennsieve App gallery + highlights)
GET /packages/assets?dataset_id=..&tag=highlight
GET /packages/assets?dataset_id=..&asset_type=thumb
GET /packages/assets?dataset_id=..&asset_type=thumb&tag=highlight

# reads — public (Discover / SPARC.science / Epilepsy.science)
GET /packages/discover/assets?dataset_id=..&tag=highlight
GET /packages/discover/assets?package_id=..&asset_type=thumb

# tag management (EditFiles)
POST   /packages/assets/{id}/tags            {"tag":"highlight"}
DELETE /packages/assets/{id}/tags/highlight

# highlight ordering (EditFiles)
PUT    /packages/assets/highlights/order?dataset_id=..   {"ordered_ids":["id1","id2",..]}
```

## Rollout order

1. Merge + run the `viewer_asset_tags` migration in **pennsieve-db-migrations** on Dev.
2. Deploy the packages-service changes to Dev.
3. Validate gallery + highlights end-to-end (Pennsieve App + a discover app).
4. Promote to prod (migration first, then service).

## Known gap (out of scope, flag for a ticket)

Migration `V20260523120300__alter_viewer_assets_for_chat.sql` states that packages-service
should restrict chat-scoped reads (`chat_session_id IS NOT NULL`) to the asset's `created_by`
user. `handleGet` (`assets.go`) currently authorizes on dataset RBAC only and does **not**
enforce this. Not relevant to highlights (those are `chat_session_id IS NULL`), but worth a
follow-up ticket.
