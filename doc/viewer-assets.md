# Viewer Assets

Viewer assets are auxiliary files associated with packages in a dataset that power interactive visualizations in the Pennsieve web application. They are distinct from the source files a user uploads — they are derived artifacts (e.g., OME-Zarr pyramids, Neuroglancer precomputed volumes, Parquet UMAP plots) generated by compute workflows and stored alongside the original data.

## Data Model

### Relationships

```
Dataset
 └── Package (source file)
       └── Viewer Asset (1 or more per package)
             └── S3 objects (the actual files)
```

- A **viewer asset** belongs to exactly one **dataset**.
- A viewer asset can be linked to **zero or more packages** (many-to-many via a junction table).
  - An asset with **one or more** package links is *package-scoped*: it visualises data from those specific packages.
  - An asset with **zero** package links is *dataset-scoped*: it represents data at the dataset level (e.g. a cohort-wide UMAP). Scope is derived from the current state of the junction table — there is no `scope` column — and an asset can move between scopes by editing its `package_ids` via PATCH.
- Each viewer asset maps to a set of files stored under a single S3 prefix.

### Database Tables

Viewer assets are stored in the **organization-scoped PostgreSQL schema** (`"{org_id}"`):

**`viewer_assets`**

| Column       | Type      | Description                                      |
|--------------|-----------|--------------------------------------------------|
| `id`         | UUID      | Primary key                                      |
| `dataset_id` | int       | Foreign key to `datasets`                        |
| `name`       | string    | Human-readable name (e.g., `"umap-projection"`)  |
| `asset_type` | string    | Type identifier (e.g., `"ome-zarr"`, `"parquet-umap-viewer"`) |
| `properties` | JSONB     | Arbitrary metadata for the viewer                |
| `s3_bucket`  | string    | Bucket where files are stored                    |
| `status`     | string    | Lifecycle state: `created` or `ready`            |
| `created_by` | int       | User ID                                          |
| `created_at` | timestamp |                                                  |

**`viewer_asset_packages`** (junction table)

| Column            | Type | Description                        |
|-------------------|------|------------------------------------|
| `viewer_asset_id` | UUID | Foreign key to `viewer_assets.id`  |
| `package_id`      | int  | Foreign key to `packages.id`       |

### S3 Storage Layout

All viewer asset files live under a deterministic prefix:

```
s3://{bucket}/viewer-assets/O{OrgID}/D{DatasetID}/{AssetID}/
```

Example:
```
s3://pennsieve-storage/viewer-assets/O19/D2049/a1b2c3d4-e5f6-7890-abcd-ef1234567890/
  ├── data.parquet
  ├── metadata.json
  └── config.yml
```

### Asset Status Lifecycle

```
created  ──(files uploaded)──>  ready  ──(deletion)──>  cleanup queue  ──(async)──>  S3 objects removed
```

- **`created`**: Record exists, upload in progress. Not yet visible to viewers.
- **`ready`**: All files uploaded. Available to the front-end.
- On **deletion**, a database trigger queues the S3 prefix for async cleanup by a separate Lambda.

## End-to-End Workflow: Creating Viewer Assets

The typical flow is driven by a **Step Functions workflow** that orchestrates compute processors. The final stage invokes the `data-target-assets` processor, which creates the viewer asset record and uploads the generated files.

```
 ┌──────────────────────────────────────┐
 │  Step Functions Orchestrator         │
 │  (invokes compute processors)       │
 └──────────────┬───────────────────────┘
                │
                ▼
 ┌──────────────────────────────────────┐
 │  Upstream Processor                  │
 │  (e.g., generates UMAP parquet      │
 │   files and writes to INPUT_DIR)    │
 └──────────────┬───────────────────────┘
                │
                ▼
 ┌──────────────────────────────────────────────────────────────────┐
 │  data-target-assets processor                                    │
 │                                                                  │
 │  1. Discover files in INPUT_DIR                                 │
 │  2. Resolve package IDs from the execution run                  │
 │  3. POST /packages/assets  →  creates record + gets credentials │
 │  4. Upload files to S3 using temporary STS credentials          │
 │  5. PATCH /packages/assets/{id}  →  status = "ready"           │
 └──────────────────────────────────────────────────────────────────┘
```

### Step-by-Step Detail

#### 1. File Discovery

The processor recursively walks `INPUT_DIR`, following symlinks, and collects all files to upload. No transformation occurs at this stage — the upstream processor has already produced the final asset files.

#### 2. Package ID Resolution

The processor determines which packages the asset should be linked to:

- If `PACKAGE_ID` is explicitly set, that single package is used.
- Otherwise, it fetches the execution run from the workflow service (`GET /compute/workflows/runs/{runId}`) and extracts package IDs from the run's data sources.

#### 3. Create Asset Record (POST /packages/assets)

The processor calls the packages-service API to create the viewer asset:

**Request:**
```json
{
  "name": "umap-projection",
  "asset_type": "parquet-umap-viewer",
  "properties": { "dimensions": 2, "metric": "cosine" },
  "package_ids": ["N:package:abc-123"]
}
```

**Response:**
```json
{
  "asset": {
    "id": "a1b2c3d4-...",
    "name": "umap-projection",
    "asset_type": "parquet-umap-viewer",
    "status": "created",
    "s3_bucket": "pennsieve-storage"
  },
  "upload_credentials": {
    "access_key_id": "ASIA...",
    "secret_access_key": "...",
    "session_token": "...",
    "expiration": "2026-04-10T15:00:00Z",
    "bucket": "pennsieve-storage",
    "region": "us-east-1",
    "key_prefix": "viewer-assets/O19/D2049/a1b2c3d4-.../"
  }
}
```

The response includes **temporary STS credentials** scoped to the asset's S3 prefix. These credentials only allow `PutObject` and multipart upload operations and expire after 1 hour.

#### 4. Upload Files to S3

Using the temporary credentials, the processor uploads each file via multipart upload (64 MB parts, SHA-256 checksums). The file's relative path within `INPUT_DIR` is preserved under the S3 key prefix.

#### 5. Mark Asset as Ready (PATCH /packages/assets/{id})

After all files are uploaded, the processor sets the asset status to `ready`:

```json
{ "status": "ready" }
```

The asset is now available for front-end viewers to consume. Discover lists only `ready` assets, so an asset that never gets this PATCH stays hidden there.

## Packages-Service API Reference

### Authenticated Endpoints

All authenticated endpoints require `token_dataset_auth` (JWT via API Gateway authorizer).

#### POST /packages/assets

Create a viewer asset and receive temporary upload credentials.

- **Permission**: `EditFiles`
- **Query params**: `dataset_id` (required)
- **Returns**: 201 with asset record and `upload_credentials`
- **Errors**: 404 if `package_ids` includes a package that is in the trash or was replaced. The message names those packages, and no asset is created. Unknown packages, or packages from another dataset, are skipped as before.

#### GET /packages/assets

List viewer assets for a dataset. Operates in three modes:

- **`package_id` supplied** — returns assets linked to that package (*package-scoped*).
- **`package_id` omitted** — returns assets in the dataset that have **no package links** (*dataset-scoped*).
- **`scope=all`** — returns every non-chat asset in the dataset, linked to packages or not.

Settings:

- **Permission**: `ViewFiles`
- **Query params**:
  - `dataset_id` (required)
  - `package_id` (optional)
  - `scope` (optional) — only `all`. Any other value → 400. `scope` with `package_id` → 400.
  - `asset_type` (optional) — exact match, e.g. `thumb`. Works in every mode.
  - `status` (optional) — `created` or `ready`. Anything else → 400. Works in every mode.
  - `limit` (optional) — 1–500, else 400. Defaults to 100 with `scope=all`.
  - `offset` (optional) — 0 or more, else 400.
- **Order**: `created_at`, newest first. Ties are broken by asset `id`, so pages are stable.
- **Paging**: with `scope=all` the list is always paginated. In the other two modes it is only paginated when `limit` or a non-zero `offset` is passed, so existing callers get the same result as before.
- **Returns**: Array of assets (each with `asset_url`, `package_ids` and `packages`) plus CloudFront signing params. Paginated lists also have `total_count`, `limit` and `offset` (see [List response fields](#list-response-fields)).
- **Errors**: 400 for a bad `scope`, `status`, `limit` or `offset`, or for a `package_id` that is unknown or in another dataset. 404 for a `package_id` that is in the trash or was replaced.

**Removed packages are hidden.** A package is *removed* when it is in the trash (`state` `DELETING` or `DELETED`) or was replaced by a newer upload (`replaced_by_package_id` set). This applies to the list, single GET, PATCH and POST responses:

- Removed packages are left out of each asset's `package_ids` and `packages`.
- With `scope=all`, an asset whose package links **all** point to removed packages is not listed. Assets with no links still are.
- `?package_id=<removed package>` returns 404 ("package is in the trash or was replaced").
- Links are never deleted. Restoring a package from the trash brings its assets back.

#### PATCH /packages/assets/{asset_id}

Update an asset's status, properties, or linked packages.

- **Permission**: `EditFiles`
- **Query params**: `dataset_id` (required)
- **Body fields** (all optional): `status`, `properties`, `package_ids`
- **Validation**: `status`, when given, must be `created` or `ready`. Anything else (including `Ready` or `complete`) → 400, and nothing is changed.
- **Errors**: 404 if `package_ids` includes a package that is in the trash or was replaced. The message names those packages, and nothing is changed (not the links, not the other fields). Unknown packages, or packages from another dataset, are skipped as before. Replacing `package_ids` keeps the asset's hidden links to removed packages, so a restore from the trash still brings them back.

#### DELETE /packages/assets/{asset_id}

Delete an asset record and queue its S3 objects for cleanup.

- **Permission**: `EditFiles`
- **Query params**: `dataset_id` (required)
- **Returns**: 204

#### Known gap: chat-figure reads (needs a ticket)

Migration `V20260523120300__alter_viewer_assets_for_chat.sql` says chat-scoped reads (`chat_session_id IS NOT NULL`) should be limited to the asset's `created_by` user. The service doesn't enforce that yet:

- `GET /packages/assets/{asset_id}` and `GET /packages/assets` check dataset permissions only.
- `GET /packages/assets?package_id=` (package mode) still lists chat figures linked to the package.

### Public Endpoint (Discover)

#### GET /packages/discover/assets

List viewer assets for a published package or dataset. No authentication required.

- **Query params**: exactly one of
  - `package_id` — the **source package node ID** (e.g. `N:package:abc-123`). Returns assets linked to that package.
  - `dataset_id` — the **published-dataset PK** as an integer, i.e. `discover.public_datasets.id` (the same numeric ID that appears in `https://discover.pennsieve.io/datasets/{id}` URLs). Returns dataset-scoped assets (those with no package links).
- **Latest version only**: only the dataset's **latest** `PUBLISH_SUCCEEDED` version counts. A package is public only if it has a file in that version.
  - `package_id` mode: 404 if the package is not in the latest succeeded version. That includes a package that is only in a failed version, or only in an older version.
  - Each asset's `package_ids` and `packages` list only packages in the latest version.
- **Optional**:
  - `scope=all` (only with `dataset_id`) — returns every asset in the published dataset instead: assets with no package links, plus assets with at least one link to a package in the latest version. This filter runs before paging. Use it to load a dataset's gallery thumbnails in one call. Assets linked only to unpublished packages (e.g. files added after publication) are left out.
  - `asset_type` — exact match, e.g. `thumb`. Works in every mode.
  - `limit` — 1–500, else 400. Defaults to 100 with `scope=all`.
  - `offset` — 0 or more, else 400.
  - There is no `status` param. Discover only returns `ready` assets.
- **Only finished assets** (`status: ready`) are returned, in every mode. Assets still uploading are hidden.
- **Chat figures** (`chat_session_id` set) are never returned, in every mode.
- **Validation**: Checks the Discover database to confirm the package or dataset is published. Note the asymmetry: the package side accepts a *node ID* (because `discover.public_file_versions` stores `source_package_id` as a node ID), while the dataset side accepts the *published-dataset integer PK* (because `discover.public_datasets` does not store the source dataset node ID).
- **Order and paging**: same as the authenticated list. Newest first, ties broken by asset `id`. Always paginated with `scope=all`; otherwise only when `limit` or a non-zero `offset` is passed.
- **Returns**: Array of assets (each with `asset_url`, `package_ids` and `packages`) plus CloudFront signing params. Each `packages` entry also has `file_path`. The list also has `version` (see [List response fields](#list-response-fields)).
- **Errors**: 400 if neither or both of `package_id`/`dataset_id` are supplied, if `dataset_id` is non-numeric, if `scope` is anything other than `all` or is combined with `package_id`, or if `limit` or `offset` is out of range. 404 if the package/dataset is not published, the package is not in the latest published version, or the dataset has no `PUBLISH_SUCCEEDED` version (e.g. only a failed or embargoed one).

### Response Fields

#### `packages` on each asset

Every asset, on both endpoints, has a `packages` array. This covers the list, single GET, PATCH and POST responses.

```json
"packages": [
  { "package_id": "N:package:abc-123", "name": "scan.png" }
]
```

- `package_id` is the package node ID. `name` is the package name.
- On Discover, each entry also has `file_path`: the package's file path inside the published dataset, e.g. `files/scan.png`.
- `packages` is `[]` when there are none.
- `package_ids` is unchanged and still returned, for compatibility.

#### List response fields

| Field | When present | Meaning |
|-------|--------------|---------|
| `total_count` | Paginated lists only | All matching assets, ignoring `limit` and `offset` |
| `limit` | Paginated lists with a limit (absent when only `offset` is passed) | The page size used |
| `offset` | Paginated lists only | The offset used |
| `version` | Discover only | The latest published version number used |

A list is paginated when `limit` or a non-zero `offset` is passed, or with `scope=all`. An unpaginated authenticated list looks exactly like before, apart from the new `packages` field.

## Accessing Viewer Assets from the Front-End

1. **List assets** for a package using `GET /packages/assets` (authenticated) or `GET /packages/discover/assets` (public).
2. Each asset in the response includes an `asset_url` — the full CloudFront base URL for that asset's files.
3. The response also includes `cloudfront` signing params (`policy`, `signature`, `key_pair_id`).
4. Construct file URLs by appending the relative file path to the asset's `asset_url` and adding the signing params as query parameters.
5. Signed policies expire after **1 hour**.

Example response:
```json
{
  "assets": [
    {
      "id": "a1b2c3d4-...",
      "name": "ome-zarr",
      "asset_type": "ome-zarr",
      "asset_url": "https://assets.pennsieve.net/abc123ef/O19/D2049/a1b2c3d4-.../",
      "status": "ready",
      "package_ids": ["N:package:..."],
      "packages": [
        { "package_id": "N:package:...", "name": "scan.png" }
      ]
    }
  ],
  "cloudfront": {
    "policy": "eyJ...",
    "signature": "gkv...",
    "key_pair_id": "K135..."
  }
}
```

With `scope=all` (or `limit` / a non-zero `offset`) the response also has `total_count`, `limit` and `offset`. On Discover it also has `version`, and each `packages` entry has `file_path`.

Example file URL construction:
```
{asset_url}{relative_path}?Policy={policy}&Signature={signature}&Key-Pair-Id={key_pair_id}

https://assets.pennsieve.net/abc123ef/O19/D2049/a1b2c3d4-.../.zattrs?Policy=eyJ...&Signature=gkv...&Key-Pair-Id=K135...
```

## Authentication

| Context | Mechanism |
|---------|-----------|
| Front-end / user API calls | JWT token via API Gateway authorizer (dataset-scoped) |
| data-target-assets processor | Callback token: `Authorization: Callback workflow-service:{runId}:{token}` |
| S3 upload | Temporary STS credentials (1-hour TTL, scoped to asset prefix) |
| S3 read (front-end) | CloudFront signed policy (1-hour TTL) |

## Asset Cleanup

A scheduled Lambda (`packages-service-asset-cleanup`) runs every hour. It:

1. Polls the `viewer_asset_cleanup_queue` table (up to 100 entries per run).
2. Deletes all S3 objects under each queued prefix.
3. Removes the queue entry after successful deletion.

This ensures S3 storage is reclaimed even if inline deletion during the `DELETE` API call fails or times out.
